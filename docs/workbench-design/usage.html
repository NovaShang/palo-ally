Claude 用量

左侧栏加一项「Claude 用量」，在「主机与设备」上面，第二行直接写最紧的那条额度还剩多少。点开是一页：还剩多少、什么时候重置、会不会用完，下面是账号和登录。登录过期时，同一页最上面就是「重新登录」。

稿子里的账号、数字、agent 都是编的。下面这个可以点：切状态，点「Claude 用量」开页面，点「重新登录」「换个账号」「退出登录」。

要你定的（2 件）

入口、页面、重新登录、换账号、退出登录，我估约 8 小时。

1. 入口放在哪按你说的画成左侧栏的一行，样子和别的行一样。缺点是 agent 多了要滚到底才看得见。另一种是底栏 ＋ 和设置之间的胶囊，一直看得见，也不占行。两种在上面都能切。
2. 额度用完，恢复时自动接着做我建议做，约多 2 小时。现在 agent 停了就停了，还会写「模型那边太忙了」，说得不对。

我替你定了两件：退出登录这次就做，放最后一行，先问再退；「本周谁用得多」先不做，Claude 不给每个 agent 的用量，只能估。

1. 入口

一行，标题「Claude 用量」，下面直接写答案：「本周剩 43%」。圆环是已用的比例，和指示器外圈同一套颜色：平时灰，用到 80% 橙，95% 红。取已用比例最高的那条，所以它说的总是最先碰到的。

  • 紧挨着「主机与设备」：都是管这台电脑的，一天看几次，不压过 Palo 和工作区。
  • 它的页面开着时，这一行选中，和别的行一样。
  • 底栏那种：＋ 和设置之间的空处，同一种玻璃、同样高度（Mac 34，手机 48）。要把底栏换成系统软边，行滑到下面会淡掉，Mac 上还没试过。

各种状态下这一行怎么写

2. 页面

Mac 在主区打开，标题在标题栏中间，和「主机与设备」一样；内容宽 664，和设置页一样，不拉满，长条才读得清。手机是推进去的一页。

  • 每条额度三行：名字和剩余、进度条、重置时间和会不会用完。
  • 条填的是已用的部分，和上下文那条一个方向，也和 Claude Code 的 /usage 一致；空着的就是剩的。
  • 条上的细线是时间走到哪儿了。条没到细线，说明比时间走得慢；过了细线，就是用得偏快。
  • 「会不会用完」只按这个窗口到现在的平均速度算，算法在第 6 节。窗口刚开始（不到 10%）不写。

3. 各种状态

用完了，Mac

停下的 agent 用闲着的灰色图标，不用橙色：它们没在等你。第二行写几点接着做。本来就在等你的不变。终端里开着的 agent，Palo 不会替它接着做。

4. 登录

动作主机现在能不能要新做的正在干活的 agent要不要先问
重新登录（已过期）能，整套都有：授权页、粘贴代码、恢复后接着做只是多一个入口：这一页最上面已经停了，登录好后接着做不问
重新登录（还没过期）基本能。开始登录的代码不检查是否过期（读代码）登录页的字现在写死「过期了」「停下的事会接着做」，要按情况写；成功后主机要把空闲的进程重开不打断，做完这一轮再重开（推断，要实测）不问。登录成功之前一切照旧（推断，要实测）
换个账号同一套登录，主机不能替你选账号，是你在授权页里换登录前后比对邮箱，说清换成了谁；空闲的马上重开，在干的做完这一轮再换这一轮还用旧账号，下一轮用新账号（推断，要实测）先问
退出登录还没有。命令有：claude auth logout（只看了帮助，没有跑过）新接口；先停下所有在跑的并记下来；「在电脑上登录了」的检测要改，它靠比对钥匙串日期，退出后那一项没了先停下，重新登录后接着做先问，红色
存几个账号来回切做不到。Claude Code 默认一台电脑只存一个登录每次都要走一遍授权

账号写邮箱。现在 App 里哪儿都不显示账号，主机也没读过；这页要新加。只在这页显示，不进日志和推送。

5. 第二步：本周谁用得多

6. 每个数从哪来

「看到」是 2026-11 在 SDK 0.3.322 上真的调了一次、没发任何消息，只看字段和类型。「读到」是只在类型说明里有。

页面上的来自可靠吗
有哪几条额度、顺序、名字rate_limits.limits[]：kind group scope.model.display_name看到有，但这个方法的返回类型里没写它（只在另一个类型 SDKUsageReport 里）。没有时退回 five_hour seven_day model_scoped
剩 %100 减 percent（或 utilization）看到，都是整数。看到过 five_hour 是 null，所以有几条画几条，不写死。session 那条叫「5 小时」是读说明推的
几点重置resets_at看到，标准时间。类型允许 null，空就不写这句
时间细线、会不会用完窗口开头 = resets_at 减 5 小时或 7 天；用完时刻 = 开头 + 已过时间 ÷ 已用比例自己算的。只是平均速度，不知道你接下来要干什么。早于重置才写时间
圆环和条的颜色我们自己的 80% / 95%和指示器一致。Claude 也给 severity，不用
套餐名subscription_type、accountInfo().subscriptionType看到。只有 pro / max / team / enterprise，分不出 Max 的档位
邮箱、组织accountInfo()看到。两台主机邮箱和组织都一样就当同一个账号
没有套餐额度rate_limits_available 为 false；apiProvider apiKeySource 说是哪种读到。说明里写订阅账号缺权限时也会是 false，要单独写一句
用完了（马上知道）轮次里的 rate_limit_event：status: rejected、resetsAt读到，没发消息所以没看到。主机现在直接丢掉它
停在这里的 agent轮次失败且 errorCategory 是 rate_limit读到。现在和「服务器太忙」混在一起，要结合上一行分开
额外用量开着extra_usage.is_enabled看到。只写开没开，不写钱；用到 80% 才出现
谁用得多主机扫对话记录（SpendMeter 现在按价钱算每天每个会话），换成占比估算。SDK 的 behaviors.agents 只按子 agent 类型分，不认识 Palo 的 agent

多久更新一次

  • 向正开着的助理进程问，不另起进程。看到：第一次 0.2 秒，紧接着再问 4 毫秒，说明它自己有缓存；另起一个进程要 4 秒。
  • 页面开着每分钟问一次；有 agent 在干，每 10 分钟一次；都闲着就不问。到了重置时间问一次。轮次里带来的额度消息到了就更新。
  • 一直不问 behaviors：它要扫最近 7 天的全部对话，看到要 2.7 秒。

拿不到的

  • 具体多少条、多少 token，Claude 只给百分比。
  • Max 是哪一档、每天用了多少、每个 agent 占额度的真实比例。
  • 这个方法名字里就写着「实验，别依赖」，SDK 升级可能没了或改了。没了就退到只显示账号和登录，这一行不写剩多少。
